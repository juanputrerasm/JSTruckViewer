# 4x4 Evolution truck format (TRK v6 and v7)

## Scope

This document describes the truck manifest, model and texture formats that 4x4 Evolution (2000) and 4x4 Evolution 2 (2001) use, as read by JSTruckViewer. Both games are the same Terminal Reality lineage as Monster Truck Madness, and the manifest is recognisably the same line-oriented text, but three layers changed: the container is POD2, the models are `.SMF` rather than `.BIN`, and the textures carry a real opacity channel.

Everything below was verified against the stock `TRUCK.POD` of both games: 121 Evo 1 manifests and 150 Evo 2 manifests, 567 models totalling 5,403 drawable groups, and the 783 textures those models reference.

## Container: POD2

Evo ships its trucks in POD2, a signed and indexed archive rather than POD1's bare directory.

| Offset | Size | Field |
|---|---|---|
| `0x00` | 4 | `"POD2"` |
| `0x04` | 4 | Archive CRC-32/MPEG-2 over `0x08`..EOF |
| `0x08` | 80 | NUL-terminated comment, the archive's display name |
| `0x58` | 4 | Directory entry count |
| `0x5C` | 4 | Audit-trail record count |
| `0x60` | n × 20 | Directory records |
| … | variable | NUL-terminated name table, then the payloads, then the audit trail |

Each 20-byte directory record is five little-endian `uint32`:

| Offset | Field |
|---|---|
| `0` | Offset of the entry's path within the name table |
| `4` | Payload length |
| `8` | Absolute payload offset |
| `12` | Unix timestamp |
| `16` | Payload CRC-32/MPEG-2 |

The name table runs from the end of the directory to the first payload. The viewer bounds its read that way rather than scanning to EOF, so a corrupt path offset cannot walk into megabytes of texture data looking for a NUL. The CRCs are read but not verified, and the audit trail — fixed 312-byte records appended after the payloads — is skipped entirely, which is what lets Evo 2's 144 MB `TRUCK.POD` index in a single pass.

Both stock archives put every path under `ART\`, `MODELS\` or `TRUCK\`, using backslashes, which normalise to the same `ART/`, `MODELS/`, `TRUCK/` prefixes the MTM paths use.

## Manifest: TRK v6 and v7

An Evo manifest opens with a version pair instead of an `MTM2` header:

```text
version
6                                  6 = 4x4 Evolution, 7 = 4x4 Evolution 2
truckName
Chevrolet Blazer TrailBlazer 4WD
truckMake
Chevrolet
...
signature: C89BC44E D3A8FB4D // WARNING: Do not edit this file
```

That first line is how the viewer tells the generation apart: MTM2 manifests open with `MTM2` or `MTM2.1`, MTM1 manifests open with the bare `truckName` label, and Evo manifests open with `version`.

### What differs from the MTM2 dialect

| Aspect | MTM2 | 4x4 Evolution |
|---|---|---|
| Header | `MTM2 truckName` then the name on its own line | `version` then `6` or `7` |
| Wheel anchors | Three pairs: `faxle.rtire.static_bpos.x`, `.y`, `.z` | One vec3 line: `faxle.rtire.static_bpos` → `+2.385,-0.700,+5.360` |
| Models | `.BIN`, named by stem or file name | `.SMF`, named by stem |
| Scrape points | `Scrape point N` label per point | One `sc[].pt` label followed by an uncounted run of vec3 lines |
| Counted lists | None | `xm.gear_ratio[]`, `xm.gearInertia[]`, `eng.torqueTable[]`, `stockPartList[]`, `colorList[]` |
| Showroom data | None | Make, model, class, model year, price, team requirement |
| Paint | None | `numColors` / `colorList[]` |
| Axle, bars, driveshaft | Present | Absent — see below |
| Integrity | None | Trailing `signature:` line |

### Counted lists

A `<name>[]` label is followed by N bare value lines with no labels of their own. Four of the five take their count from an earlier scalar field:

| List | Count field |
|---|---|
| `xm.gear_ratio[]` | `xm.maxGear` |
| `xm.gearInertia[]` | `xm.maxGear` |
| `eng.torqueTable[]` | `eng.torqueTableCount` |
| `stockPartList[]` | `numStockParts` |
| `colorList[]` | `numColors` |

`xm.gear_ratio[]` is the one label that carries a trailing comment naming the gears, and the comment changes with the gear count — `xm.gear_ratio[] - Park/Reverse/Neutral/1st/2nd/3rd` through `.../4th/5th` across the stock corpus — so the label must be matched on everything up to the `[]`, not on the whole line.

`sc[].pt` has no count anywhere. Its run is read while the lines still parse as three comma-separated numbers, which is unambiguous because every label that can follow it is non-numeric. Every stock truck has exactly 12.

### Paint schemes

Each `colorList[]` entry is `hue,saturation,brightness,red,green,blue,textureName`: an HSV shift the garage applies to the truck, the RGB swatch shown for it, and a decal texture. Every entry in both stock archives names `NULL` for that texture. The viewer reports the swatches and does not repaint the body, because it has no genuine example of the decal case to check a repaint against.

### Absent chassis hardware

All 271 stock manifests name `NULL.BIN` for `axleModelName`, `NULL.RAW` for `barTextureName`, and `NULL` for the instrument cluster. Evo bodies model their own suspension as ordinary geometry — the `.SMF` group named `AxleR`, for instance — so the viewer assembles body plus four tires plus lights and greys out the axle, axle-bar, shock and driveshaft toggles, the same way it does for MTM1.

`shockTextureName` is `susp.raw` throughout and the texture exists in `ART`, but with no axle to anchor a shock between, nothing is drawn from it.

## Models: .SMF

`.SMF` ("C3DModel") is ASCII, one value per line:

```text
C3DModel
fileVersion
objectCount
lodEnabled,lodSwitchHeight              only when fileVersion >= 4

repeat objectCount:
    groupName
    visible                             only when fileVersion >= 2
    objectVersion
    vertexCount,frameCount,faceCount,objectInfo
    "v1"                                only in the Evo 2 bump form
    specular,specularLevel,shininess,transparent,reflective,textureName
    "bumpTextureName"                   only in the Evo 2 bump form
    repeat frameCount:
        repeat vertexCount: x,y,z,nx,ny,nz,u,v
    repeat faceCount: i0,i1,i2
```

A vertex line and a face line are both just comma-separated numbers, so the counts are the only thing that distinguishes them. The reader is a counted state machine for that reason, and every face index is checked against the group's vertex block before it is used.

Every model in both stock truck archives is `fileVersion` 4 with `objectVersion` 1, every group is flagged visible, and every Evo 2 group carries the `v1` bump form while no Evo 1 group does. Frame counts above 1 appear in the track models but not in the truck ones; frames after the first are read only to keep the cursor aligned with the face block.

### Materials

Fields 0-2 of the material line are lighting scalars. The stock corpus writes a small set of combinations — `1/0.25/32`, `1/1/64`, `1/1/32`, `1/0/0`, `1.25/0/0` — consistent with specular strength, specular level and a Phong exponent. The viewer carries them through under neutral names rather than asserting a meaning it has not confirmed.

Field 3 is transparency and field 4 reflectivity. Transparency appears only on glass and light-lens groups — never on a `Body` group in either archive — and the coverage behind it is a real 8-bit plane, so those groups are blended rather than alpha-tested. Alpha-testing them at 0.5, which is right for MTM's colour-keyed textures, would turn a soft lens into a stencil.

### Axes and winding

`.SMF` is Y-up and in feet, the same unit the manifest's own anchors use. The viewer's model space is Z-up and also in feet, so the conversion is a straight axis swap: model `(x, y, z)` = Evo `(x, z, y)`.

That swap flips handedness, which is what the scene wants. Truck meshes are drawn with `THREE.BackSide` because `.BIN` geometry is wound inward, so leaving the `.SMF` winding untouched puts these faces on the same side. Normals are negated for the same reason: `THREE.BackSide` compiles `FLIP_SIDED`, which negates the vertex normal, so a normal handed over pointing inward leaves the shader pointing outward.

The winding direction is not inferred — it is measured. Taking `cross(v1 - v0, v2 - v0)` against the group's own stored vertex normals agrees on 1,786 of 1,812 faces of `TRBLAZ.SMF` and 1,802 of 1,812 of `TRAILBLAZER.SMF`, and on every face of the tire models.

V likewise runs top-down, measured by correlating model Y against V: the flat-mapped wheel-hub discs give a correlation of exactly -1.000 in both games. The scene uploads its textures with `flipY`, so V is inverted on the way in, exactly as the `.BIN` path inverts its own.

### LOD

LOD is a separate file, not a group flag. `TRBLAZ.SMF` is the full-detail body and `TRBLAZ0.SMF` the reduced one, whose groups are the same names with an `L` suffix — `BodyL`, `BushBarL`, `SkidL`. No file mixes a group with its own `L` partner, so picking the right file is the whole of LOD selection and no group filtering is needed.

This is the opposite of the MTM convention, where a higher numeric suffix means *higher* detail. The viewer therefore does not run its numbered-suffix LOD search on `.SMF` archives, which would otherwise pick the low-detail body whenever an exact name missed.

### Model naming

| Part | Manifest field | Resolves to |
|---|---|---|
| Body | `truckModelBaseName` | `MODELS\<stem>.SMF` |
| Tires | `tireModelBaseName` | `MODELS\<stem><tier><side>.SMF` |

Tire detail tiers are `08`, `12` and `16`, with `L` and `R` sides — the same shape MTM2 uses. The viewer takes the highest tier for all four corners.

A bare prefix search is not enough here: `Class3Tire` also matches `Class3TireB16L`, and both score 16 on the detail-tier sort, so which one a truck got would come down to POD directory order. Candidates matching exactly `<prefix><digits>[F|R][L|R].SMF` are preferred, with the loose prefix set kept only as a fallback.

## Textures

| Game | Diffuse | Opacity | Normal map |
|---|---|---|---|
| 4x4 Evolution | `.RAW` + same-stem `.ACT` | same-stem `.OPA`, when present | none |
| 4x4 Evolution 2 | `.TIF` | second TIFF sample | `<stem>_bump.TIF`, named by the model |

### Evo 1: RAW, ACT and OPA

`.RAW` images are square and unheadered, so the side comes from the byte count. Stock truck art uses 64, 128, 256 and 512 — two of which the MTM reader rejects outright, since MTM only ever ships 64 and 256.

Palettes resolve per texture, not per archive: all 149 `.RAW` textures in the stock Evo 1 truck archive have their own same-stem `.ACT`, and there is no archive-wide palette to fall back on the way MTM falls back to `METALCR2.ACT`.

An `.OPA` is one byte of opacity per pixel, and 77 of the 149 textures have one. It is applied only when it holds exactly as many bytes as the image has pixels; a mismatch means the pairing was wrong, not that the plane needs resampling.

This is why Evo textures do not go through the MTM `RAW` reader. MTM has no alpha anywhere, so its transparency is a colour key — a texel whose palette entry is pure black is cut, everything else is opaque. Evo ships genuine coverage, and treating it as a binary key would harden every soft edge.

### Evo 2: TIFF

Every Evo 2 truck texture is an uncompressed little-endian single-strip TIFF in one of two forms:

| Form | Photometric | Samples/pixel | Count | Use |
|---|---|---|---|---|
| Palette | 3 | 1 or 2 | 265 | Diffuse; the second sample is opacity |
| RGB | 2 | 4 | 319 | `_BUMP` tangent-space normal maps |

Sizes are 64, 128, 256 and 512 square. Anything outside these forms is refused with a reason rather than decoded into plausible-looking garbage.

A TIFF `ColorMap` holds three consecutive runs — all reds, then all greens, then all blues — of 16-bit values, not interleaved RGB triples. Some writers store 0..255 in the low byte instead; a map with nothing above 255 is read as already-8-bit rather than crushed to near-black.

The `_BUMP` files are tangent-space normal maps, not height maps: sampled across `TrailBlazer_bump.TIF`, R and G average 128 and B averages 253. Their fourth sample holds something else — it averages 60 and never exceeds 128 — which the viewer does not use.

Because each `.SMF` group names its bump map outright, Evo 2 needs none of the `_N` companion-name guessing the HD MTM2 path uses.
